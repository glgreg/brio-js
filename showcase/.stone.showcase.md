# Showcase

## Purpose and Design Decisions

- `showcase/` is the website of the TCC presentation (`playground.briojs.gregorium.com`, Vercel project
  `brio-js-preview`, root directory `showcase`). It replaces the older Vite showcase of the `tcc` branch, which targeted
  the 0.1 API. Three pages, built by Vite as separate entries so Monaco loads only in the IDE: the landing page
  (`index.html`), the game player (`play.html?game=<id>`) and the playground (`playground.html`); plus `credits.html`.
- The engine is not taken from npm: `scripts/build-engine.mjs` bundles `../src/index.ts` into `public/engine/brio.js`
  (ES module, backends as chunks) and writes `public/engine/types.json` (every `.d.ts`, emitted with `--noCheck`) for
  the editor. Every page, game and sandbox imports `"@brio-js/core"` through an import map pointing at
  `/engine/brio.js`, so what the site shows is always the engine of the current commit.
- Demo games are ordinary BrioJS projects in `public/games/<id>/` (an `index.html`, ES modules, assets). The player
  runs them in an iframe; the playground copies the same folder into the browser using the `project.json` manifests
  written by `scripts/build-manifests.mjs`. Templates live in `public/templates/<id>/` with the same shape.
- All demo rendering goes through the WebGL2 backend, 2D included: `lumen-vigil` draws pixel art as textured quads
  under an orthographic `BrioCamera3D`, animating sprite-sheet frames in a `BrioShader` (`sprite.glsl`) and lighting
  them with point lights. This is why `BrioTexture.filter = "nearest"` exists.
- The site is bilingual. English is the default; `src/strings.ts` types the Portuguese table against the English one,
  so a missing key fails `tsc`. Games read `?lang=pt` and keep their own `strings.js`.
- The mascot (Capibrio) is inline SVG (`src/mascot.ts`) and a procedural 3D model built from primitives
  (`public/games/araucaria-run/capybara.js`), shared by the landing page scene and Araucária Run.

## Invariants

- The playground's IndexedDB schema is shared by `src/ide/db.ts` and `public/sw.js`: database `brio-playground`
  version 1, store `projects` (keyPath `id`) and store `files` (keyPath `[project, path]`, index `project`). The
  service worker serves `/sandbox/<project>/<run>/<path>` straight from that store, so a change to one side without the
  other breaks every running game.
- `<run>` changes on every Run, which gives the game a fresh module graph; the worker ignores it when reading files.
  HTML served from the sandbox gets the import map (unless the page has one) and `/sandbox-bridge.js`, which forwards
  console output and errors to the IDE with `postMessage` (same origin only).
- Assets whose license forbids redistribution live in `public/games/*/assets/vendor/`, which is ignored by git: today
  the BDragon1727 holy spell sheets of Lumen Vigil. They reach Vercel only through CLI deploys from a machine that has
  them (`.vercelignore` at the repository root keeps the rest of the local folders out). Without them the game falls
  back to plain glowing materials, so git-based builds still work.
- Every third-party asset is credited in `src/games.ts` (shown on the player and credits pages); its license file is
  kept next to it when the pack ships one.
- `vercel.json` uses `cleanUrls` and `trailingSlash: true`: game folders are addressed as `/games/<id>/`, so their
  relative URLs keep working after the redirect from `index.html`.

## Integration Contracts

- Build: `bun install && bun run build` inside `showcase/` (Vercel runs exactly this), which runs the engine build,
  the manifests and `vite build` into `showcase/dist/`. It needs the parent directory (`../src`, `../tsconfig.json`).
- Game query parameters: `lang=en|pt`; `demo=1` (attract mode, also used by `scripts/capture-posters.mjs` to
  render `poster.webp`); `t=<seconds>` in Lumen Vigil to start later in the night.
- Playground URL parameters: `template=<game or template id>` (reuses the last project made from it, or copies it),
  `project=<id>`, `run=1`.

## Anti-Patterns

- Importing the engine with a relative path or from npm inside a game: the sandbox and the player resolve only the
  `"@brio-js/core"` import map entry.
- Committing files from a `vendor/` folder, or adding an asset without checking its license and adding its credit.
- Using `prompt()` / `confirm()` in the IDE: they block the page (and browser automation); the IDE has its own dialog.
