# Snapshots and Persistence

## Purpose and Design Decisions

`BrioSerializer` captures and restores an `ECSWorld` as one binary `Uint8Array` (ADR 0005). Because authoritative
spatial state lives in contiguous `TypedArray`s, a checkpoint is a series of bulk `TypedArray.set` copies with no
object graph traversal or `JSON.stringify`, which keeps checkpoints and `restart()` cheap during gameplay.
`toJSON` / `fromJSON` translate to and from `SerializedSnapshotJSON` for export and debugging only.

`BrioStorage` exposes four fixed static adapters: `state` (module-level `Map`), `session` and `local` (Web Storage
with JSON encoding) and `db` (`AsyncDatabaseStorage` over IndexedDB, which stores `Uint8Array` snapshots natively
through `saveSnapshot` / `loadSnapshot`).

Binary layout (`Uint32` words in platform byte order, sections 4-byte aligned): header `[magic "BRIO" 0x4F495242,
version, highWaterMark, activeCount, freeListLength, layoutFlags]`, then free-list ids, alive flags (padded to 4
bytes), component masks, `transform2D` (only if the layout has 2D), `transform3D` (only if it has 3D), collider,
rigidBody and visual, each covering slots `0 .. highWaterMark - 1`. Version 1 had a 5-word header and always both
transform sections.

## Invariants

- The format is versioned: `restoreSnapshot` accepts versions 1 and 2 and rejects others, so saves already stored
  keep loading after format changes. A version 1 snapshot restores into any layout (missing buffers are skipped); a
  version 2 snapshot must match `storage.layoutFlags` exactly, so a 3D save cannot silently lose data in a 2D world.
- Every check runs before `world.clear()`: magic, version, capacity (`highWaterMark <= capacity`), layout,
  `activeCount` / free-list length against the high-water mark, the body length implied by the header, and each
  free-list id (below the high-water mark, not alive, not duplicated). A rejected snapshot throws an `Error` and
  leaves the world untouched.
- When `byteOffset` is not a multiple of 4 the input is copied first, because `Uint32Array` / `Float32Array` views
  require aligned offsets.
- Restore marks every restored slot `TRANSFORM | COLLIDER | RENDER` dirty so static layer caches are rebuilt, and
  it calls `world.clear()`, which advances every generation: all handles are stale afterwards and are rebound with
  `bindECS(storage, id, true)` by their owner.
- Only slots below the high-water mark are written, so snapshot size scales with entities used, not capacity.

## Integration Contracts

- `BrioScene.captureState()` and `BrioGame` checkpoints pair the bytes with the registered objects and their
  `entityId`s; the bytes alone do not know which facade owns which slot.
- Not in the snapshot: generations, JS-side facade fields (flip, sprite, collision, hierarchy), timers, cameras and
  lights. Visibility is included through the `visual` buffer. `BrioGame` stores its `BrioRandom` state next to the
  bytes.
- `AsyncDatabaseStorage` opens database `brio_game_db`, store `brio_kv_store`, schema version 1. When IndexedDB is
  missing or fails to open it falls back to an in-memory `Map` (copying `Uint8Array`s), so data does not persist
  across reloads. The fallback is observable: `isPersistent()` resolves the backend, and `persistent` is `true` /
  `false` once known (`undefined` before the first operation).
- `session` / `local` store each key as `"brio:" + key` (`BrioStorage.webStoragePrefix`), so `clear()` removes only
  the engine's keys and leaves the rest of the origin. Values written before the prefix existed are still read
  (`get` / `has` fall back to the bare key), moved under the prefix by `set`, and removed by `delete`; `clear()`
  does not see them. Both fall back to an in-memory map when `window` or the storage is unavailable; values that
  are not valid JSON are returned as raw strings.

## Format Version 3 and Compatibility (v0.2)

- `captureSnapshot()` writes version 3: an 11-word header (magic, version, high-water mark, active count, free-list
  length, layout flags, then the strides of the 2D transform, 3D transform, collider, rigid body and visual sections).
- Compatibility contract: every engine version reads all earlier format versions (1 and 2 imply the strides of the
  current storage). Component fields are only appended to a stride, never reordered or removed. When a snapshot
  section has a different stride, `restoreSnapshot()` copies entity by entity: the common prefix is kept, missing
  trailing fields read as `0` and extra ones are dropped. A newly appended field must therefore treat `0` as its
  default, or come with a migration in the serializer.
- `BrioSerializer.FORMAT_VERSION` is the written version; `BrioSerializer.inspect(bytes)` reads the header without
  restoring (version, layout, counts, strides, `supported`). Unknown versions are rejected with an `Error` naming
  the supported range, before the world is touched. Buffers whose length is not a multiple of 4 are rejected.
- Snapshots hold ECS data only. Checkpoints (`BrioGame` / `BrioScene` `captureState`) add the state that lives on the
  facades (see the objects stone); persisting that state is not covered yet (`docs/ROADMAP.md`, "Before 1.0").

## Anti-Patterns

- Storing snapshots in `local` / `session`: values go through `JSON.stringify`, which turns a `Uint8Array` into an
  index-keyed object. Binary snapshots belong in `BrioStorage.db` (or go through `toJSON` first).
- Writing game data into `localStorage` / `sessionStorage` directly and expecting `BrioStorage.local.clear()` to
  remove it: only prefixed keys written through the adapter are cleared.
- Adding or resizing ECS buffers without bumping `BRIO_SNAPSHOT_VERSION` and keeping a reader for older versions.
- Calling `toJSON` in the game loop; it allocates arrays and strings by design.

Discrepancies: ADR 0005 calls the JSON layer "lazy-loaded" and mentions a `SceneSnapshot` type. In code, `toJSON` /
`fromJSON` are static methods of `BrioSerializer` (no lazy loading) and scenes use `BrioSceneState` plus a raw
`Uint8Array`. `toJSON` reports the version of its input (`fromJSON` always re-encodes as the current version). The
adapters are a fixed set with no registration API.
