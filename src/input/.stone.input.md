# Input Controllers

## Purpose and Design Decisions

The module turns asynchronous DOM events into state that gameplay code queries synchronously inside `update()`. Each
device is an opt-in controller created by `BrioGame.useKeyboard()`, `useMouse()`, `useTouch()` and `useGamepad()` and
exposed as `game.keyboard`, `game.mouse`, `game.touch` and `game.gamepad` (the getters throw if the `useX()` call is
missing).

- **Level state plus latched edges**: DOM listeners write the current level (`down`/`up`) into maps and record press
  and release edges in per-controller `Set`s. `isPressed`/`isUp` read those latches, and `endFrame()` consumes them
  once per frame. A press and release that both happen between two frames therefore still report `isPressed` and
  `isUp` for exactly one frame (the old "taps shorter than one frame are lost" known issue). A keydown for a key
  already held (OS key repeat) is not a new press edge.
- **`BrioKeyboard`** stores `KeyboardEvent.key` strings in two `Map<string, boolean>` objects that `BrioGame` owns
  (`#keyboardState`, `#keyboardPrevState`) and injects through the constructor. `endFrame()` consumes the latches and
  overwrites the previous-state map from the current one. Until `endFrame()` has run once, `isPressed`/`isUp` fall
  back to comparing the two maps, so an external owner that snapshots the maps itself (older `BrioGame`, the
  existing tests) keeps the old behavior. `preventDefaultKeys` (arrows, Space, Tab) suppresses page scrolling while
  leaving browser shortcuts such as F5/F12 alone. `customActions` maps a key to a callback run synchronously inside
  `keydown`.
- **Global keyboard state**: `BrioKeyboard.globalIsDown` / `globalIsUp` use separate static state with a lazily added
  `window` listener; every controller also forwards its events there (idempotent static helpers, so both paths
  never double-count a release). `syncGlobalFrame()` closes the global frame; after its first call, `globalIsUp`
  reads latched releases.
- **`BrioMouse`** keys buttons by `MouseEvent.button` index (`MouseButton` names map 0..4) and latches edges the same
  way; `endFrame()` (already called by `BrioGame`) consumes them and zeroes `delta`/`wheelDelta`. Positions are
  converted to canvas pixels by scaling with `canvas.width / rect.width`, so a CSS-scaled canvas still reports
  backbuffer coordinates. `mouseup` is listened on `window` so a release outside the canvas still clears the button.
  `getWorldPosition(camera, scale = 1, out?)` delegates to `BrioCamera2D.screenToWorld` with the canvas size and
  `game.scale`, so rotated cameras and split-screen viewports map correctly.
- **`BrioTouch`** keeps a `Map<identifier, TouchPoint>` with `startX/startY`; it uses the same canvas scaling, passive
  listeners, and `touchend`/`touchcancel` on `window`. It has no per-frame edge detection (`isTouching`, `touchCount`,
  `touches`, `primaryPosition` only).
- **`BrioGamepad`** has no listeners: `poll()` reads `navigator.getGamepads()` once per frame (called at the start of
  `#step`), keying buttons as `"<padIndex>:<buttonIndex>"` with W3C Standard Gamepad names (`south`, `r1`, `home`...).
  Sticks use a radial deadzone (default `0.15`, clamped to `[0, 0.9]`) rescaled so output still reaches magnitude 1.
  `vibrate()` uses `vibrationActuator.playEffect("dual-rumble")` and swallows rejections.
- **Focus loss**: keyboard, mouse and touch listen to window `blur` and document `visibilitychange` (hidden) and call
  `releaseAll()`: held keys and buttons go up and report `isUp` on that frame, and active touches are cleared.

## Invariants

- `endFrame()` (keyboard, mouse) and `syncGlobalFrame()` run exactly once per frame, after the user `update()`
  callback, scene step and render. A second call in the same frame consumes edges before game code sees them; a
  missing call makes a latched edge report `true` forever.
- Listener attachment is idempotent. `attach()` does nothing while attached and `removeListener()` does nothing while
  detached. Constructing a controller detaches any controller already attached over the same state map (keyboard)
  or the same event target (mouse, touch), tracked in static `WeakMap`s, so repeated `useKeyboard()`/`useMouse()`/
  `useTouch()` calls never stack DOM listeners. The replaced controller keeps working as plain state but receives
  no more events.
- Keyboard keys are case-sensitive `KeyboardEvent.key` values (`"z"` and `"Z"` differ with Shift) because the maps
  store the raw key string.
- `BrioGamepad.isPressed`/`isUp` depend on `poll()` running once per frame before game code; polling twice in one
  frame erases the transition. Gamepad edges are sampled, not latched: a button tapped between two polls is missed,
  because the Gamepad API exposes no events for buttons.
- Every listener-based controller keeps its handler references so `removeListener()` detaches exactly what it
  attached. Per-frame work (`endFrame`, `releaseAll`, snapshots) iterates with handlers bound once in the
  constructor, so it does not allocate closures.

## Integration Contracts

- `BrioGame.#step` order: `gamepad.poll()`, fixed steps (`fixedUpdate`), `update()` callback, scene, cameras, render,
  then the input frame end: keyboard `endFrame()` (which also snapshots the previous-state map), `mouse.endFrame()`
  and `BrioKeyboard.syncGlobalFrame()`. Every fixed step of a frame sees the same edge state.
- Controllers are exported from `src/index.ts` as `Keyboard`, `Mouse`, `Touch`, `Gamepad` with the `MouseButton`,
  `TouchPoint` and `GamepadButtonName` types.

## Anti-Patterns

- Relying on `customActions` for per-frame logic: callbacks fire on every `keydown`, including OS key-repeat events,
  and outside the game loop.
- Reading `isPressed` in code that runs on its own timer (`setTimeout`, promises): the edge boundary is the frame,
  not the call.
- Keeping a reference to an old `game.keyboard`/`game.mouse` across a second `useX()` call: the old controller is
  detached and stops receiving events.

Deferred: per-frame buffered transitions for the gamepad and `BrioInputMap` (action bindings) stay planned for v0.2
(docs/ROADMAP.md).
