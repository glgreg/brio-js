# Input Controllers

## Purpose and Design Decisions

The module turns asynchronous DOM events into state that gameplay code queries synchronously inside `update()`. Each
device is an opt-in controller created by `BrioGame.useKeyboard()`, `useMouse()`, `useTouch()` and `useGamepad()` and
exposed as `game.keyboard`, `game.mouse`, `game.touch` and `game.gamepad` (the getters throw if the `useX()` call is
missing).

- **Level state from events, edges from snapshots**: DOM listeners write the current level (`down`/`up`) into maps;
  `isPressed` and `isUp` compare that map against a copy taken at the end of the previous frame. No event queue is
  kept, so the API is cheap and allocation-free per query.
- **`BrioKeyboard`** stores `KeyboardEvent.key` strings in two `Map<string, boolean>` objects that `BrioGame` owns
  (`#keyboardState`, `#keyboardPrevState`) and injects through the constructor; the game copies current into previous
  at the end of `#step`. `preventDefaultKeys` (arrows, Space, Tab) suppresses page scrolling while leaving browser
  shortcuts such as F5/F12 alone. `customActions` maps a key to a callback run synchronously inside `keydown`.
- **`BrioMouse`** keys buttons by `MouseEvent.button` index (`MouseButton` names map 0..4). Positions are converted to
  canvas pixels by scaling with `canvas.width / rect.width`, so a CSS-scaled canvas still reports backbuffer
  coordinates. `delta` and `wheelDelta` accumulate during the frame and are zeroed by `endFrame()`. `mouseup` is
  listened on `window` so a release outside the canvas still clears the button. `getWorldPosition(camera)` delegates
  to `BrioCamera2D.screenToWorld`.
- **`BrioTouch`** keeps a `Map<identifier, TouchPoint>` with `startX/startY`; it uses the same canvas scaling, passive
  listeners, and `touchend`/`touchcancel` on `window`. It has no per-frame edge detection (`isTouching`, `touchCount`,
  `touches`, `primaryPosition` only).
- **`BrioGamepad`** has no listeners: `poll()` reads `navigator.getGamepads()` once per frame (called at the start of
  `#step`), keying buttons as `"<padIndex>:<buttonIndex>"` with W3C Standard Gamepad names (`south`, `r1`, `home`...).
  Sticks use a radial deadzone (default `0.15`, clamped to `[0, 0.9]`) rescaled so output still reaches magnitude 1.
  `vibrate()` uses `vibrationActuator.playEffect("dual-rumble")` and swallows rejections.

## Invariants

- Edge queries (`isPressed`, `isUp`) are valid only because the previous-state snapshot is taken exactly once per
  frame, after the user `update()` callback, scene step and render. A second snapshot in the same frame would make
  every press invisible; a missing one would make a press report `true` forever.
- A press and release that both happen between two frames are lost by `isPressed`/`isUp` (known issue in
  docs/ROADMAP.md); `isDown` is the reliable query. The v0.2 plan is per-frame buffered transitions plus `BrioInputMap`.
- Keyboard keys are case-sensitive `KeyboardEvent.key` values (`"z"` and `"Z"` differ with Shift) because the maps
  store the raw key string.
- `BrioGamepad.isPressed`/`isUp` depend on `poll()` running once per frame before game code; polling twice in one
  frame erases the transition.
- Every listener-based controller (keyboard, mouse, touch) keeps its handler references so `removeListener()` detaches exactly what it attached.

## Integration Contracts

- `BrioGame.#step` order: `gamepad.poll()`, fixed steps (`fixedUpdate`), `update()` callback, scene, cameras, render,
  then keyboard snapshot and `mouse.endFrame()`. Every fixed step of a frame sees the same edge state: a press is seen
  by all fixed steps of that frame, or by none when the frame runs zero fixed steps.
- `BrioKeyboard.globalIsDown` / `globalIsUp` use a separate static state with a lazily added `window` listener. The
  engine never calls `BrioKeyboard.syncGlobalFrame()`, so `globalIsUp` stays `false` unless the caller syncs it.
- Controllers are exported from `src/index.ts` as `Keyboard`, `Mouse`, `Touch`, `Gamepad` with the `MouseButton`,
  `TouchPoint` and `GamepadButtonName` types.

## Anti-Patterns

- Calling `useKeyboard()`/`useMouse()`/`useTouch()` more than once: each call attaches a new set of DOM listeners and
  the old instance is dropped without `removeListener()`.
- Relying on `customActions` for per-frame logic: callbacks fire on every `keydown`, including OS key-repeat events,
  and outside the game loop.
- Reading `isPressed` in code that runs on its own timer (`setTimeout`, promises): the snapshot boundary is the frame,
  not the call.
- Assuming held state resets when the page loses focus: no controller listens to `blur`, so a key or button held
  while focus is lost stays `isDown` until its release event arrives.

Discrepancies noted from the code: the `game.mouse` JSDoc example uses `game.mouse.isPressed(0)` while the signature
takes a `MouseButton` name; the `useGamepad()` JSDoc mentions `gamepadconnected` listeners that `BrioGamepad` does not
register.
