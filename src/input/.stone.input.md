# Input Controllers

## Purpose and Design Decisions

The module turns asynchronous DOM events into state that gameplay code queries synchronously inside `update()`. Each
device is an opt-in controller created by `BrioGame.useKeyboard()`, `useMouse()`, `useTouch()` and `useGamepad()` and
exposed as `game.keyboard`, `game.mouse`, `game.touch` and `game.gamepad` (the getters throw if the `useX()` call is
missing).

- **Level state plus latched edges**: DOM listeners write the current level (`down`/`up`) into maps and record press
  and release edges in per-controller `Set`s. `isPressed`/`isUp` read those latches, and `endFrame()` consumes them
  once per frame. A press and release that both happen between two frames therefore still report `isPressed` and
  `isUp` for exactly one frame (the old "taps shorter than one frame are lost" known issue). A keydown for a key
  already held (OS key repeat) is not a new press edge.
- **`BrioKeyboard`** stores `KeyboardEvent.key` strings in two `Map<string, boolean>` objects that `BrioGame` owns
  (`#keyboardState`, `#keyboardPrevState`) and injects through the constructor. `endFrame()` consumes the latches and
  overwrites the previous-state map from the current one. Until `endFrame()` has run once, `isPressed`/`isUp` fall
  back to comparing the two maps, so an external owner that snapshots the maps itself (older `BrioGame`, the
  existing tests) keeps the old behavior. `preventDefaultKeys` (arrows, Space, Tab) suppresses page scrolling while
  leaving browser shortcuts such as F5/F12 alone. `customActions` maps a key to a callback run synchronously inside
  `keydown`.
- **Letter case**: Shift changes `key` for letters, so `w` can go down as `"w"` and up as `"W"`. A `keyup` of a
  single letter therefore also releases its other-case variant (`otherLetterCase`), which keeps the original from
  staying stuck down. Shifted digits and symbols (`"1"` vs `"!"`) depend on the layout and are not reconciled.
  `pressedKeys` exposes the live set of keys pressed this frame (used by `BrioInputMap.captureNext`).
- **Global keyboard state**: `BrioKeyboard.globalIsDown` / `globalIsUp` use separate static state with a lazily added
  `window` listener; every controller also forwards its events there (idempotent static helpers, so both paths
  never double-count a release). `syncGlobalFrame()` closes the global frame; after its first call, `globalIsUp`
  reads latched releases.
- **Pointer space** (`InputSpace.ts`): `mapClientToTarget` converts client coordinates for mouse and touch. On a
  canvas it scales by `logicalSize.width / rect.width` when the controller's `logicalSize` is set (any live
  `{ width, height }`, typically the game, read on every event so resizes apply at once), otherwise by the backing
  store `canvas.width / rect.width`. With a HiDPI backing store (`width * devicePixelRatio`), `logicalSize` keeps
  positions in game pixels. Elements that are not canvases use element-local CSS pixels, `window` uses client pixels.
- **`BrioMouse`** keys buttons by `MouseEvent.button` index (`MouseButton` names map 0..4, `MOUSE_BUTTON_NAMES`) and
  latches edges the same way; `endFrame()` (already called by `BrioGame`) consumes them and zeroes
  `delta`/`wheelDelta`. `mouseup` is listened on `window` so a release outside the canvas still clears the button.
  `getWorldPosition(camera, scale = 1, out?)` delegates to `BrioCamera2D.screenToWorld` with the same canvas size the
  positions use (`logicalSize` when set) and `game.scale`, reusing one screen-space object, so rotated cameras and
  split-screen viewports map correctly without allocating.
- **Pointer lock**: `requestPointerLock(options?)` locks the pointer to the target element and returns a promise;
  browsers whose `requestPointerLock()` returns `undefined` settle it through `pointerlockchange`/`pointerlockerror`.
  A non-element target or a missing API rejects. `isPointerLocked` mirrors `document.pointerLockElement === target`,
  updated by `pointerlockchange` (listened on `document` with the other listeners, so attachment stays idempotent).
  While locked, `position` stays frozen and `delta` accumulates raw `movementX/Y` (unscaled, for mouse-look); after
  unlock the first move re-bases `position` without a delta spike. `exitPointerLock()` only exits a lock this target
  holds; `removeListener()` rejects a pending request but leaves an active lock alone.
- **`BrioTouch`** keeps a `Map<identifier, TouchPoint>` with `startX/startY`; it uses the same pointer space, passive
  listeners, and `touchend`/`touchcancel` on `window`. It has no per-frame edge detection (`isTouching`, `touchCount`,
  `touches`, `primaryPosition` only).
- **`BrioGamepad`** has no listeners: `poll()` samples `navigator.getGamepads()` into preallocated per-pad typed
  arrays (`down`, `pressed`, `released`, analog `values`, `axes`; up to 8 pads, 32 buttons, 16 axes) without
  allocating. Every read (`isDown`, `getAxis`, `getButtonValue`, sticks) comes from the latest poll, so a frame sees
  one consistent snapshot. Edges are latched like the event controllers: once `endFrame()` has run, `poll()` may be
  called any number of times and edges accumulate until `endFrame()`; before that, every `poll()` starts a new edge
  frame (the previous poll-once behavior). A pad that disconnects releases its held buttons (`isUp`). Buttons use
  W3C Standard Gamepad names (`GAMEPAD_BUTTON_NAMES`). Sticks use a radial deadzone (default `0.15`, clamped to
  `[0, 0.9]`) rescaled so output still reaches magnitude 1. `vibrate()` uses
  `vibrationActuator.playEffect("dual-rumble")` and swallows rejections.
- **`BrioInputMap`** maps action names to `InputBinding`s, a discriminated union on `device`: keyboard key
  (`KeyboardKey`, plain strings accepted as shorthand), mouse button, gamepad button (`pad` defaults to 0), gamepad
  axis direction (`axis`, `direction`, `threshold` default `0.5`) and touch (any finger down). Bindings are
  validated and stored as frozen normalized copies inside a per-action state created at bind time, so queries walk
  dense arrays and never allocate. Single-letter key bindings match both cases. The map reads the controllers
  assigned through the constructor, `setControllers()` or the `keyboard`/`mouse`/`gamepad`/`touch` properties;
  a missing controller makes its bindings report up/`0`.
  - Aggregation: `isDown` is true while any binding is down. `isPressed` is true when the action was up at the
    previous `endFrame()` and a binding is down now or reports a latched press edge (sub-frame taps count).
    `isUp` is true when no binding is down and the action was down at the previous `endFrame()` or was tapped this
    frame, so a tap reports `isPressed` and `isUp` together. Pressing a second binding while the action is held is
    not a new press, and a release plus re-press within one frame while held is not either. `value()` is the
    maximum binding strength in `[0, 1]` (gamepad buttons report analog values, axes their deflection past the
    gamepad deadzone, others 0/1); axis bindings count as down from `threshold`, so `value()` can be positive while
    `isDown` is false. `axis(neg, pos)` is `value(pos) - value(neg)`. Unknown actions report `false`/`0`.
  - Changing bindings (`bind`, `rebind`, `unbind`, `load`) re-syncs the action's previous-frame state, so an input
    already held when it gets bound does not report a press.
  - Persistence: `toJSON()` returns `{ version: 1, actions: { name: InputBinding[] } }` (copies);
    `load(json, { onlyKnownActions? })` and `fromJSON` accept that object or its JSON string. Structural problems
    (not an object, other `version`, `actions` not an object, a non-array value) throw before anything changes;
    invalid bindings and skipped actions are reported in `{ applied, issues }`. Actions absent from the data keep
    their bindings (defaults for actions added later survive old saves), an action whose entries are all invalid
    keeps its bindings, and an empty array unbinds. `bind()`/`rebind()` throw on invalid bindings (programming
    errors), atomically.
  - `captureNext({ devices?, signal? })` resolves with the next key, mouse button or gamepad button press, detected
    in `endFrame()` from the controllers' latched presses. The frame in which the capture starts is skipped (the
    click or key that opened the prompt), letters resolve lowercase, and every action query reports `false`/`0`
    while a capture is pending so the captured press does not also fire gameplay or menu actions. A new capture,
    `cancelCapture()` or the signal rejects the pending one (`AbortError` / `signal.reason`). Axes are not captured.
- **Focus loss**: keyboard, mouse and touch listen to window `blur` and document `visibilitychange` (hidden) and call
  `releaseAll()`: held keys and buttons go up and report `isUp` on that frame, and active touches are cleared.

## Invariants

- `endFrame()` (keyboard, mouse) and `syncGlobalFrame()` run exactly once per frame, after the user `update()`
  callback, scene step and render. A second call in the same frame consumes edges before game code sees them; a
  missing call makes a latched edge report `true` forever.
- Listener attachment is idempotent. `attach()` does nothing while attached and `removeListener()` does nothing while
  detached. Constructing a controller detaches any controller already attached over the same state map (keyboard)
  or the same event target (mouse, touch), tracked in static `WeakMap`s, so repeated `useKeyboard()`/`useMouse()`/
  `useTouch()` calls never stack DOM listeners. The replaced controller keeps working as plain state but receives
  no more events.
- Keyboard keys are case-sensitive `KeyboardEvent.key` values (`"z"` and `"Z"` differ with Shift) because the maps
  store the raw key string.
- `BrioInputMap.endFrame()` runs exactly once per frame after game code and before the controllers' `endFrame()`:
  it reads the controllers' latched presses (for `captureNext`) and snapshots every action's down state. Without it,
  `isPressed` stays true while an action is held.
- Gamepad edges are latched between polls but the samples themselves are discrete: a button pressed and released
  between two consecutive `poll()` calls is never seen, because the Gamepad API exposes no button events. Extra
  polls (for example from a timer between frames) shorten that window; polls within one synchronous frame step add
  little. Without `endFrame()`, `poll()` must run exactly once per frame, since each poll starts a new edge frame.
- Every listener-based controller keeps its handler references so `removeListener()` detaches exactly what it
  attached. Per-frame work (`endFrame`, `releaseAll`, snapshots) iterates with handlers bound once in the
  constructor, so it does not allocate closures.

## Integration Contracts

- `BrioGame.#step` order: `gamepad.poll()`, fixed steps (`fixedUpdate`), `update()` callback, scene, cameras, render,
  then the input frame end: `BrioInputMap.endFrame()` first, then keyboard `endFrame()` (which also snapshots the
  previous-state map), `mouse.endFrame()`, `gamepad.endFrame()` and `BrioKeyboard.syncGlobalFrame()`. Every fixed
  step of a frame sees the same edge state.
- `BrioGame` owns one `BrioInputMap` (`game.input`) and assigns each controller to it when `useKeyboard()`,
  `useMouse()`, `useTouch()` or `useGamepad()` creates one; mouse and touch get `logicalSize = game`.
- Controllers are exported from `src/index.ts` as `BrioKeyboard`, `BrioMouse`, `BrioTouch`, `BrioGamepad` and
  `BrioInputMap` (`Brio.Keyboard`, `Brio.InputMap` and so on in the default namespace) with the `MouseButton`,
  `TouchPoint` and `GamepadButtonName` types, the input map binding, JSON and capture types and `InputLogicalSize`.
- `KeyboardKey` (`src/tools/base_types.ts`) is a strict union; `event.key` is cast to it at the DOM boundary and
  JSON key bindings are accepted as any non-empty string, since the union cannot be checked at runtime.

## Anti-Patterns

- Relying on `customActions` for per-frame logic: callbacks fire on every `keydown`, including OS key-repeat events,
  and outside the game loop.
- Reading `isPressed` in code that runs on its own timer (`setTimeout`, promises): the edge boundary is the frame,
  not the call.
- Keeping a reference to an old `game.keyboard`/`game.mouse` across a second `useX()` call: the old controller is
  detached and stops receiving events.
- Reading `BrioInputMap` actions to cancel a pending `captureNext()`: queries are suppressed while capturing, so a
  "press Escape to cancel" check reads `game.keyboard.isPressed("Escape")` inside `update()` and calls
  `cancelCapture()` before the frame ends.
- Using `mouse.delta` as canvas-space motion while locked: it is raw `movementX/Y`, unscaled by the canvas.

Not covered: touch bindings have no latched edges (a touch shorter than one frame is lost) and no screen regions
(virtual buttons); gamepad axes cannot be captured by `captureNext()`.
