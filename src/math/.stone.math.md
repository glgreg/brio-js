# Math Library

## Purpose and Design Decisions

The math module is the zero-dependency numeric foundation of the engine (ADR-0001, ADR-0002). It is written as free
functions grouped in ES modules so bundlers can drop what a game does not use.

- **Functional, out-parameter style**: `vec2.ts`, `vec3.ts`, `quat.ts` and `mat4.ts` export functions such as
  `add(out, a, b)` that write into `out` and return it. Callers reuse scratch objects, so hot paths (transforms,
  rendering) allocate nothing per frame. `src/math/index.ts` re-exports them as namespaces `Vector2`, `Vector3`,
  `Quaternion`, `Matrix4` and `BrioMath`; `*Self` variants (`addSelf`, `normalizeSelf`...) mutate the first argument.
- **Structural types**: `Vec2`, `Vec3` and `Quat` are plain `{ x, y[, z][, w] }` interfaces, so any object literal
  works. `Mat4` is a `Float32Array(16)` in column-major order (translation in `[12..14]`), uploadable to GPU uniforms
  without conversion.
- **Reactive views** (`BrioVec2`, `BrioVec3`, `BrioQuat`): classes whose `x/y/z/w` accessors are defined per instance
  with `Object.defineProperties`. When bound with `bindBuffer(buffer, offset, adopt)` they read and write a slot of an
  ECS `Float32Array` directly; `onChange` lets the owner (e.g. `BrioTransform2D`) mark dirty bits. `BrioVec2.setSilent`
  writes without firing `onChange` so a hook can sanitize values without recursion (`BrioVec3`/`BrioQuat` lack it). `unbindBuffer()` copies the slot back
  into local fields so a recycled ECS slot is never written again.
- **Projection conventions**: `perspective`, `orthographic` and `lookAt` are right-handed with OpenGL clip depth
  `[-1, 1]` (`perspective` supports `far = Infinity`). `transformPoint` performs the perspective divide.
- **`BrioRandom`**: xoshiro128** with SplitMix32 seeding and FNV-1a hashing of string seeds. It is chosen because it
  is fast in 32-bit integer JS arithmetic (`Math.imul`, `>>> 0`) and yields identical sequences on every platform,
  which replays, checkpoints and the planned MCP headless simulation (ADR-0006) need. State is four `Uint32` words
  exposed through `state` (copy on read) for capture and restore.
- **`BrioCollision`**: static narrow-phase tests over object colliders: `isColliding` (rect/square AABB, circle,
  circle vs AABB), `computeMTV`, `resolveCollision` (only when both colliders are `"solid"`), `isColliding3D` (box,
  sphere, sphere vs box), and `addSquare`/`addRectangle`/`addCircle` that attach a collider to a `BrioObject2D`.

## Invariants

- Vector/matrix functions never allocate when given an `out`, and `Matrix4.multiply` is safe when `out` aliases `a` or
  `b`. Callers depend on both properties to use scratch storage.
- `normalize` of a zero vector yields zero rather than `NaN`, so direction math on stationary objects stays finite.
- A bound reactive vector reads from its buffer, not from its private fields; `bindBuffer` without `adopt` overwrites
  the slot with the local value. ECS slot reuse depends on `unbindBuffer()` before a slot is released.
- xoshiro128** never holds the all-zero state: `reseed` and the `state` setter force `s[0] = 1` in that case, because the
  all-zero state outputs zeros forever.
- `BrioRandom` output for a given seed is part of the replay contract: changing the algorithm, the seeding, or the
  number of draws a helper consumes (e.g. `int`, `pick`, `shuffle` each use `next()`) changes every saved replay.
- Colliders are axis-aligned and positioned at `transform.position + collision.pos`; rotation, scale and pivot are
  ignored. Circle and sphere offsets point to the top-left corner of the bounding box (center = pos + radius), radius
  is `min(size.x, size.y) / 2` in 2D and `size.x / 2` in 3D.
- AABB overlap uses strict inequalities (touching edges do not collide), while circle tests use `<=` (touching counts).

## Integration Contracts

- `objects` binds `BrioVec2`/`BrioVec3`/`BrioQuat` to ECS slots; `BrioTransform3D` converts rotations with
  `Quaternion.fromEuler`/`toEuler`. `BrioGame` owns `game.random` (seed via config `seed`) and stores its `state` in
  checkpoints.
- `BrioCollision` imports `BrioObject2D`/`BrioObject3D` types from `objects` and is used by `BrioObject2D`
  (`addCollisionMask`) and `BrioTileMap`. This is a compile-time dependency on `objects` that the frontmatter
  `depends_on: []` does not record.
- `src/math/index.ts` does not re-export `BrioRandom` or `BrioCollision`; they are exported from `src/index.ts` as
  `Random` and `Collision`.

## Anti-Patterns

- Using `BrioMath.randomRange`/`randomInt` or `Math.random()` in gameplay: they use `Math.random()` and break
  determinism; `game.random` (a `BrioRandom`) is the reproducible source.
- Allocating vectors inside per-frame loops (`Vector2.create()`, object spreads) instead of reusing `out` scratch
  objects.
- Holding a reference to a reactive vector after its owner was destroyed without unbinding: writes would land in a
  slot now owned by another entity.
- Feeding these projection matrices to a backend with `[0, 1]` clip depth (WebGPU) without a depth remap; the `Mat4`
  JSDoc claims direct WebGPU compatibility, which the `[-1, 1]` depth formulas do not support.

Discrepancies noted from the code: the `fromEuler` JSDoc says "intrinsic XYZ", but its formula is the Z-Y-X intrinsic
(extrinsic X-Y-Z) composition; `toEuler` uses the matching roll-pitch-yaw formula, so the pair round-trips. `computeMTV`
for circle vs rectangle falls through to the AABB branch and treats the circle as its bounding box. `Vector2.clamp`
returns `undefined` when `min > max`, while `Vector3.clamp` has no such check.
