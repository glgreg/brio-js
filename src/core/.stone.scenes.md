# Scenes, Layers, Viewports and Timers

## Purpose and Design Decisions

`src/core` holds the scene-level containers that `BrioGame` drives and `BrioCompositor` renders.

- `BrioScene` is an isolated stage (GLOSSARY "Scene") with its own `ECSWorld(maxEntities)`, `BrioTimer`, layers,
  2D/3D objects, cameras and lights. Content registered directly on `BrioGame` acts as the default scene; the active
  `BrioScene` is composed after it. `preload(fn)` and `load(fn)` only store callbacks; `game.setScene()` runs
  `collectPreloadAssets()`, loads the assets, then `mount(assets)`, which registers the returned `SceneContent` in
  order (layers, then cameras and lights, then objects) and captures `#initialState` for `restart()`.
- `BrioLayer` is a rendering plane with `order` and a `LayerPolicy`: `"static"` (offscreen cache per camera,
  redrawn only when stale), `"parallax"` (camera offset times `scrollFactor`), `"dynamic"` (redrawn every frame,
  culled) and `"ui"` (screen space, `scrollFactor` forced to 0). `getSortedObjects()` re-sorts by `transform.layer`
  only when an insertion happened or an adjacent pair is out of order.
- `BrioViewport` is a normalized rectangle (`x`, `y`, `width`, `height` clamped to `[0, 1]`) with presets for
  split-screen, quad and minimap layouts; each camera owns one and `toPixelRect` maps it to the surface.
- `BrioRegistry<T extends { name }>` keeps a `Map` for name lookup and a dense array for hot-loop iteration;
  `sortIfNeeded(compare)` sorts in place only when an adjacent pair is out of order.
- `BrioTimer` schedules `after`, `every` (optional iteration count) and `tween` (progress 0..1) tasks advanced by
  `update(dt)`; handles expose `cancel`, `pause`, `resume` and `isActive`.

## Invariants

- `BrioRegistry.list` is mutated in place (`push`, `splice`, `length = 0`, in-place `sort`) and never reassigned,
  because `CompositorSource` keeps the `cameras2D`, `cameras3D`, `objects3D` and `lights` list references captured
  once in the `BrioScene` constructor. `add` with an existing name replaces the item at the same index.
- Every `BrioScene` has a `"default"` dynamic layer (created in the constructor and again in `destroy()`); objects
  added to an unknown layer name fall back to it.
- Scene objects live in the scene's world: `addObject2D` creates a `TRANSFORM_2D` entity and `addObject3D` creates a
  `TRANSFORM_3D` entity for the root and one per descendant part, so checkpoints cover model parts.
- Object names are unique per scene: adding a 2D or 3D object whose name is already registered (or the same object
  again) first releases the previous one (slots recycled, layers left, transform unbound), so no slot or layer
  membership leaks. A replaced 3D object keeps its registry position.
- The scene world layout starts with both transform buffers (or the constructor `layout`). `useLayout(layout)`
  rebuilds the world with the given layout, moving registered objects into new slots, and refuses (`false`) when a
  registered object needs a dropped buffer or a checkpoint / initial state already exists. Without a 3D buffer,
  `addObject3D` throws, matching the `"2d"` game.
- `destroy()` unbinds every root and 3D part before clearing the world.
- `restoreState` reconciles membership: objects registered after the capture are unbound (`entityId = -1`), the
  bytes are restored, and every captured object and part is rebound with `adopt = true` and its new generation, then
  returned to its captured layer if that layer is still registered.
- `step(dt)` does nothing while paused or for `dt <= 0`; it advances the timer, the scene's 2D cameras, then
  `onUpdate`. `BrioGame` calls it once per frame with the variable `deltaTime`, after fixed steps and user `update`.
- `BrioTimer.update` compacts finished tasks in place after the pass. Tasks registered by a callback during the pass
  are advanced in the same pass, and an `every` task fires several times when `dt` spans several intervals.
- `BrioLayer.isDirty` is always `true` for `"dynamic"`; for other policies it reflects `markDirty`, membership,
  order, visibility and re-sorts. The compositor calls `clearDirty()` on every layer at the end of the frame.

## Integration Contracts

- `compositorSource` (`world`, `layers` and the camera, object and light lists) is what `BrioCompositor` renders;
  static caches read `DirtyFlag.RENDER` from the scene world.
- `captureState()` returns `BrioSceneState` (`bytes`, `objects2D` with their layer, `objects3D`, `parts3D`). Game
  checkpoints embed it, and `game.restoreCheckPoint` reactivates the captured scene before restoring it.
- `createCheckpoint()` returns only the bytes. `restoreCheckpoint()` without argument, or with the exact array the
  last `createCheckpoint()` returned, restores the full state. Other bytes restore the world values: registered
  roots and 3D parts whose slot is alive in the snapshot re-adopt it, and objects whose slot is not alive are
  unregistered and detached. Bytes alone cannot re-register objects removed after the capture nor detect a slot
  recycled by another object; `captureState()` / `restoreState()` carry that information.
- `BrioGame` is expected to call `scene.useLayout({ transform2D: true, transform3D: dimension !== "2d" })` when a
  scene is registered (`addScene`), so scenes of a `"2d"` game skip 3D memory (ADR 0004).

## Anti-Patterns

- Reusing an object name for two live objects in one scene: the second registration evicts the first.
- Touching scene content right after `game.setScene()` for a scene with `preload` / `load`: activation is
  asynchronous (ROADMAP known issue); `await game.ready()` first.
- Expecting reproducible shakes from a `BrioCamera2D` registered in a scene: it uses `Math.random()` unless
  `camera.random = game.random` is assigned (ROADMAP known issue).
- Expecting timers, cameras or lights to roll back on checkpoint restore; only ECS slots and object membership do.

Discrepancies: the ADR 0004 memory saving for scenes depends on `BrioGame` calling `useLayout()`; a scene captured
or populated with 3D objects before registration keeps both buffers.
