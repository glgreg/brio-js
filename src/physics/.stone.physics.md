# Physics

## Purpose and Design Decisions

The physics module is a small toolkit that gameplay code drives explicitly; nothing in `BrioGame`, `BrioScene` or the
objects layer instantiates or steps it. Narrow-phase tests and penetration resolution live in `math`
(`BrioCollision`), so this module covers motion integration, the velocity response to a contact, and broad-phase pair
culling.

- **`BrioRigidBody`** is a standalone simulation profile, not an ECS component: it holds `velocity`, `acceleration`
  and `gravity` as `BrioVec3` (2D bodies ignore `z`), plus `mass` (clamped to `>= 1e-4`), cached `inverseMass`,
  `friction` and `restitution` (both clamped to `[0, 1]`) and `isStatic`. `integrate2D(transform, dt)` and
  `integrate3D(transform, dt)` apply semi-implicit Euler (velocity first, then position from the new velocity) and
  clear `acceleration` after each step, so `applyForce` acts for one step only while `applyImpulse` changes velocity
  immediately. Units follow the transform: pixels with y-down in 2D (e.g. gravity `{ y: 980 }`), world units in 3D.
- **Restitution** is applied by `applyCollisionResponse(separation)`: given the separation vector that pushed the body
  out of an obstacle (the MTV returned by `BrioCollision.resolveCollision(mover, obstacle)`), it reflects the velocity
  component pointing into the obstacle, `v -= (1 + restitution) * (v . n) * n`. `0` stops normal motion (the body
  slides), `1` bounces at the same speed. The obstacle is treated as immovable and the tangential component is kept;
  separating velocities, zero-length separations and static bodies are no-ops.
- **Friction** is linear velocity damping, `velocity *= max(0, 1 - friction * dt)`, a first-order approximation of
  exponential decay; it depends slightly on `dt`, so a fixed timestep (`game.fixedUpdate`) keeps it consistent.
- **`SpatialHash2D`** (default cell `128` px) and **`SpatialOctree3D`** (default cell `32` units) are uniform grids keyed
  by `"cx,cy"` / `"cx,cy,cz"` strings in a `Map`. Each object is inserted into every cell its bounds overlap;
  `getPotentialPairs(objects)` clears the grid, reinserts enabled colliders, and emits each pair once. They are rebuilt
  per query rather than updated incrementally, which keeps them stateless between frames at the cost of reallocating
  cell keys and buckets.
- Despite its name, `SpatialOctree3D` is not a hierarchical octree: it is the 3D counterpart of the uniform hash, and
  its JSDoc says so. The export keeps the name for backward compatibility; a rename (for example `SpatialHash3D` with
  a deprecated alias) is a possible future change.

## Invariants

- A static body never moves: `isStatic` sets `inverseMass` to `0`, zeroes `velocity`/`acceleration`, and makes
  `applyForce`, `applyImpulse`, `applyCollisionResponse` and both `integrate*` methods no-ops. `inverseMass` is
  recomputed whenever `mass` or `isStatic` changes, because forces and impulses multiply by it instead of dividing by
  mass.
- `integrate*` with `dt <= 0` does nothing, so paused or zero-length frames cannot corrupt state.
- Broad-phase bounds use the same convention as `BrioCollision`: `transform.position + collision.pos` as the minimum
  corner and `collision.size` as extent (a 3D sphere uses `size.x` on all axes). Diverging conventions would cause
  missed pairs that the narrow phase never sees.
- Pair deduplication keys on object identity: `insert` gives each object an index in a reused `Map` (cleared with the
  grid), and pairs are keyed by the number `min * count + max` in a reused `Set<number>`. Same-named objects therefore
  keep all their pairs, no key strings are built per pair, and an object is never paired with itself.
- Disabled colliders (`collision.enabled === false`) are never inserted. `SpatialHash2D.insert` accepts objects without
  a collider (using `transform.renderSize`), while `getPotentialPairs` only inserts objects with an enabled collider.

## Integration Contracts

- `integrate2D` writes `transform.position.x/y` through `BrioVec2` accessors, so each write reaches the ECS buffer and
  fires the transform's dirty hook; `integrate3D` does the same through `BrioVec3`.
- Candidate pairs are tuples `[a, b]` in insertion order; callers run `BrioCollision.isColliding`/`isColliding3D`
  and, for `"solid"` pairs, `BrioCollision.resolveCollision` themselves, then pass the returned MTV to
  `applyCollisionResponse` on the moving body when it has one.
- Exported from `src/index.ts` as `BrioRigidBody` (`Brio.RigidBody` in the default namespace), `SpatialHash2D`,
  `SpatialOctree3D`, and the `BrioRigidBodyOptions` type.

## Collision Events (v0.2)

- `CollisionEventSystem<T>` (`BrioCollisionEvents.ts`, internal) turns narrow-phase tests into `enter` / `stay` /
  `exit` events. `BrioGame` owns one for 2D (`BrioCollision.isColliding`) and, outside the `"2d"` preset, one for 3D
  (`isColliding3D`), and runs them once per frame after the `update()` callback and the active scene step, over the
  game objects plus the active scene's objects. Only objects with an enabled collider and a live ECS handle are
  candidates.
- Broad phase is sort and sweep on X: candidates are insertion-sorted by the left edge of their collider (nearly
  sorted between frames, so close to linear) and a pair is tested only while X extents overlap. Pairs where neither
  object has listeners are skipped.
- Each object has a pair of contact sets (previous / current) in a `WeakMap`; after detection, `enter` is queued for
  contacts not in the previous set, `stay` for contacts in both and `exit` for contacts that disappeared. A removed
  object (destroyed, unregistered, collider disabled) is no longer a candidate: its partners receive `exit` with it,
  while the removed object itself receives no callbacks.
- Events are queued and dispatched after the sets roll over, so listeners may destroy objects, change colliders or
  start new contacts; references in the queue are cleared after dispatch.
- Steady-state frames allocate nothing: sweep entries, sets, the event queue and the set visitors are reused.
  `forget()` / `clear()` (destroy paths, snapshot restores, `game.end()`) are not hot paths.
- Listeners live on the objects (`CollisionListeners`, created on first registration) and are copied to clones by
  `game.instantiate()`; they receive `(other, self)`.
- Events do not move objects. Solid separation stays explicit (`BrioCollision.resolveCollision` in `fixedUpdate`),
  and there is still no 3D contact solver.

- The sweep sorts candidates with `sortInPlace` (merge sort with a reused buffer), because candidates are added in
  registration order every frame. `BrioGame` sweeps children at their world X position, like the narrow phase.

## Anti-Patterns

- Expecting automatic bounces: there is no contact solver; bodies pass through each other unless game code runs the
  broad phase, resolves solid pairs and calls `applyCollisionResponse`. Two moving bodies exchanging momentum is not
  modeled (the obstacle is always treated as immovable).
- Expecting trigger events: no module dispatches collision or trigger enter/stay/exit events; `"trigger"` only makes
  `resolveCollision` skip displacement, and game code polls `isColliding` itself.
- Integrating in `update()` with a variable `dt` when determinism matters; `fixedUpdate` gives reproducible motion.
- Keeping long-lived references to a grid's contents across frames: `getPotentialPairs` clears and rebuilds it.

Known gaps: trigger/collision events, 3D collision resolution, a contact solver, a character controller and raycasts
are not implemented (the latter are listed under "Later" in docs/ROADMAP.md). ADR-0003 describes physics running in a
Web Worker over `SharedArrayBuffer`; the current code runs entirely on the main thread inside user callbacks.
