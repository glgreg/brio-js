# Cameras

## Purpose and Design Decisions

- Following ADR 0004, there are two concrete classes and no shared base. Both are plain objects, not ECS entities. Each holds a normalized `BrioViewport` (`x, y, width, height` in `[0, 1]`), which enables split-screen and minimaps (ADR 0003): the compositor renders one pass per camera, clipped to its viewport.
- `BrioCamera2D` is orthographic. `pos` is the top-left world position of the view, and `size` is the viewport size in pixels (minimum 1). The visible world rectangle is `size / zoom`, with `zoom` at least 0.01. `rotation` is in radians and is applied by the compositor around the viewport center. `renderX`/`renderY` add the shake offset without allocating. `renderPos` allocates.
- `follow(target, lerpFactor = 1, deadzone)` stores a `BrioObject2D` target, with the lerp factor clamped to `[0.001, 1]`. `update(dt)` moves the view center toward the target center only when the target leaves the deadzone. The blend weight is `1 - (1 - lerpFactor)^(dt * 60)`, so `lerpFactor` means "fraction per 60 Hz frame" and convergence is framerate independent (tested at 30, 60, 144 and 240 Hz).
- `shake(intensity, duration)` produces an offset decaying linearly to zero. The random source is `camera.random`, falling back to `Math.random`.
- `setBounds(minX, minY, maxX, maxY)` clamps `pos` through `setSilent` so the view stays inside the rectangle. If the view is larger than the bounds, it is pinned to `min`.
- `worldToScreen(p, space?, out?)` and `screenToWorld(p, space?, out?)` replay exactly the transform the compositor draws with (`BrioCompositor.#applyCameraTransform` plus the `game.scale` translation of `BrioSpriteRenderer`): screen = viewportOffset + C + R(-rotation) * (zoom * scale * (world - renderPos * scrollFactor) - C), with C the viewport center. `CameraScreenSpace2D` carries the optional canvas size (canvas pixels and viewport offset, with the viewport rectangle rounded like the compositor), `scale` (`game.scale`, default 1) and the layer `scrollFactor` (default 1). Without a canvas size the coordinates are viewport-local and `size` gives the rotation center, which keeps the legacy one-argument calls working. Both methods write into a module-level scratch object and accept an `out` target, so they can run without allocating.
- `BrioCamera3D` supports `"perspective"` (fov 60 degrees by default, near 0.1, far 1000) and `"orthographic"` (`orthoSize` is the half-height). `viewMatrix` and `projectionMatrix` are recomputed lazily from two dirty flags. `position`, `target` and `up` are `BrioVec3`s whose change callback marks the view dirty, so mutating `camera.position.x` works. `clearColor` is the clear color of the 3D pass (transparent when undefined).

## Invariants

- Follow snaps to the destination once the remaining distance is under `FOLLOW_SNAP_EPSILON = 0.01` world pixels, and it only writes `pos` when the value actually changes. An asymptotic lerp would otherwise move the camera by sub-pixel amounts forever and invalidate the compositor's `"static"` layer cache on every frame.
- `isVisible(object)` (2D culling) reads the shake-adjusted position directly and does not allocate, because it runs once per object per frame. It returns false for hidden objects and for objects with opacity 0 or less.
- `near` is at least 1e-4. `far` is at least `near + 1` in the constructor and `near + 1e-3` in the setter. `aspect` is at least 1e-4 and `orthoSize` at least 1e-3. These floors keep the projection matrix invertible, which `ndcToRay` requires.
- `isSphereInFrustum(center, radius)` tests the sphere against the six planes (left, right, bottom, top, near, far) extracted from the view-projection matrix (Gribb/Hartmann, OpenGL clip space) and normalized to world units. The planes are cached in a `Float64Array(24)` and rebuilt only when a `#planesDirty` flag is set; every place that dirties the view or the projection also sets it. The test is conservative near frustum corners (it may report a sphere just outside a corner as visible), never the reverse.
- `viewProjectionMatrix` writes into a preallocated `Mat4` on every access (the multiply is not cached). Callers should read it once per pass, as the compositor does.

## Integration Contracts

- The compositor writes `camera2D.size` and `camera3D.aspect` from the real viewport pixels each frame. Camera code can therefore assume `size` matches the screen region.
- `BrioGame` calls `update(dt)` on game-level 2D cameras after the user `update()` callback. `addCamera()` sets `camera.random = game.random` when it is unset.
- `screenToRay(x, y, canvasW, canvasH)` takes canvas pixels, converts them to NDC within this camera's viewport, and calls `ndcToRay`. `ndcToRay` unprojects NDC z = -1 and z = 1 through the inverse view-projection and returns `{ origin (near plane), direction (unit) }`. Orthographic cameras produce parallel rays. Both methods allocate, so they are meant for picking, not per-object loops.
- `BrioMouse.getWorldPosition(camera, scale = 1, out?)` calls `camera.screenToWorld` with the canvas size of its target (canvas pixels, viewport offset applied) and the given `game.scale`, so it works with rotated cameras and split-screen viewports.
- The compositor and `worldToScreen`/`screenToWorld` must stay in sync: a change to `#applyCameraTransform` (rotation pivot, zoom origin, scale order) needs the same change here; `tests/cameras/CamerasInputFixes.test.ts` replays the compositor calls to catch drift.

## Anti-Patterns

- Calling `pos.set()` every frame with an unchanged value, or removing the snap epsilon: both turn static layer caching into a redraw every frame.
- Expecting the compositor to cull 3D objects: `isSphereInFrustum` is a correct six-plane test, but no per-object 3D culling pass calls it yet (docs/ROADMAP.md).
- Calling `screenToWorld` without `canvasWidth`/`canvasHeight` for a camera whose viewport is not at (0, 0) while passing canvas pixels: without the canvas size the input is read as viewport-local.
- Known issue (docs/ROADMAP.md): a `BrioCamera2D` registered directly in a `BrioScene` keeps using `Math.random()` for shakes, because only `BrioGame.addCamera` injects `game.random`. The workaround is `camera.random = game.random`.
- `BrioCamera3D` has no follow or shake. Orbit and first-person controllers are planned (docs/ROADMAP.md).
